# AI Web 应用测试框架——MVP 需求说明

> 文档状态：讨论稿  
> 版本：0.3（补充黑盒优先、分级接入和自适应回放）  
> 目标读者：产品、研发、测试、架构负责人  
> MVP 核心闭环：自然语言场景 → AI 决策 + Playwright／Computer Use 探索 → 缺陷证据 → 稳定／自适应测试 → 回放验证

## 1. 产品定义

面向 Web 应用的 AI 辅助测试工具。用户用自然语言描述测试目标和预期结果，系统在隔离的测试环境中自主操作浏览器、观察页面和运行时信息、发现可疑问题，并将确认后的路径生成可维护的 Playwright 测试。探索阶段由 AI 负责理解场景和动态决策，由 Playwright 负责采集页面信息并执行浏览器动作；当 DOM／Accessibility 无法表达 Canvas、WebGL 或视觉目标时，由 Computer Use／视觉适配器提供视觉理解和动作建议，实际浏览器动作仍由 Playwright 执行。

框架采用**黑盒优先、分级增强**原则：用户无需修改被测应用源码即可开始接入、探索、生成问题报告和创建测试。系统应先利用浏览器可观测信息完成尽可能多的测试，仅在定位、状态验证或稳定回放受限时，提出 `data-testid`、测试数据接口或 Canvas App Bridge 等可选增强建议；这些增强不是开始使用框架的前置条件。

产品定位不是替代 Playwright，而是补足传统自动化在测试设计、未知路径探索、语义判断和失败诊断方面的不足。

一句话价值主张：**零改动开始探索；Playwright 始终执行，Computer Use 在视觉步骤中按需兜底。**

## 2. MVP 目标与成功标准

### 2.1 目标

MVP 必须验证以下四个假设：

1. 用户只提供高层业务场景，AI 能完成常见的 3～10 步 Web 操作流程。
2. AI 能发现并提交带有充分证据、可人工确认的有效问题。
3. AI 探索出的有效流程能够被编译为稳定、可读的 Playwright 测试。
4. 一个已经开发多年的 Web 应用可以在不修改源码的情况下，于较短时间内完成首次接入和黑盒探索。

### 2.2 建议发布门槛

以下指标用于内部验收，不作为对外 SLA：

| 指标 | 建议门槛 |
| --- | --- |
| 场景完成率 | 在固定测试环境的 30 个基准场景中，至少 80% 能在两次尝试内完成 |
| 生成用例稳定性 | 不变版本、固定数据下重复执行 5 次，成功率至少 95% |
| 缺陷报告准确率 | 注入已知缺陷的基准中，人工确认的有效报告占比至少 70% |
| 证据完整率 | 至少 95% 的失败或问题报告包含复现步骤、截图和运行日志 |
| 安全边界 | 100% 阻止访问未授权域名和未确认的破坏性操作 |
| 可观测性 | 每次运行都可追踪模型调用、浏览器动作、页面状态和最终判断 |
| 坐标依赖 | 生成的稳定回归用例中，不允许出现脱离语义目标的裸屏幕坐标 |
| 零改动首次接入 | 不修改被测应用源码，15 分钟内完成 URL、登录态、扫描和第一次探索运行 |
| 黑盒场景完成率 | 固定的历史应用基准场景中，至少 70% 能在两次尝试内完成 |
| 稳定性标记覆盖 | 100% 的生成步骤和测试带有稳定性等级及其判断依据 |

## 3. 目标用户与主要场景

### 3.1 目标用户

- QA／测试工程师：快速探索新功能并沉淀回归用例。
- 前端／全栈工程师：在提交前验证关键用户路径。
- 小型研发团队：在自动化测试覆盖不足时获得基础 E2E 能力。
- 维护历史 Web 应用的团队：在缺少测试接口、稳定 locator 或现有自动化覆盖时先进行黑盒接入。

### 3.2 核心用户场景

1. QA 输入：“使用普通用户登录，搜索商品 A，加入购物车并确认总价正确。”
2. 系统自主探索并执行该流程。
3. 系统记录每一步的页面、动作、控制台和网络信息。
4. 系统报告流程是否完成以及发现的可疑问题。
5. QA 确认有效路径和问题，必要时编辑预期结果。
6. 系统生成 Playwright TypeScript 测试。
7. QA 在同一环境回放生成测试并下载或复制代码。

对于 Cesium 等重 Canvas 应用，典型场景还包括：通过 DOM 工具栏切换图层，由 AI 识别 Canvas 中的地图目标，由 Playwright 执行缩放、拖拽或点击，再通过应用测试桥接接口确认相机、实体和选中状态。

## 4. MVP 范围

### 4.1 必须支持

- Chromium 桌面浏览器。
- 由团队控制的开发／测试／预发布环境。
- 同一主域名及显式配置的允许域名。
- Playwright 同时作为探索阶段的页面采集／动作执行层，以及稳定和自适应回放阶段的主测试引擎。
- 在不修改被测应用源码的情况下完成项目创建、登录录制、兼容性扫描、黑盒探索和结果报告。
- DOM、ARIA／Accessibility Tree 和截图的混合观察。
- Computer Use／视觉适配器作为 Canvas、WebGL、图表、遮挡和 DOM 定位失败场景的视觉 fallback。
- Canvas／WebGL 的点击、拖拽、缩放和视觉状态观察；首批重点支持 Cesium 与 DOM 混合应用。
- 可选的应用测试桥接接口，用于读取 Canvas 内部语义状态、实体 ID、屏幕位置和加载状态。
- 常用操作：导航、点击、输入、清空、选择、勾选、滚动、悬停、返回、刷新和等待。
- 常用确定性断言：URL、文本、元素可见性、元素状态、数量和页面标题。
- AI 语义检查，但只作为“建议／可疑问题”，不直接阻断 CI。
- 每次运行的截图、动作轨迹、控制台错误和失败网络请求。
- 稳定回放和自适应回放两种模式；后者仅用于视觉步骤或黑盒模式下无法稳定定位的步骤。

### 4.2 明确不做

- Firefox、WebKit、移动端和桌面原生应用。
- 生产环境自主探索。
- 跨应用、跨浏览器标签页的长流程自动化。
- 验证码、短信、扫码和硬件密钥自动破解或绕过。
- 支付、删除真实数据、发布内容等未经确认的高风险操作。
- 完整视觉回归平台或 Figma 像素级还原检查。
- 无人审核的自动修复、静默自愈和自动提交代码。
- 对任意网站承诺完全“零脚本”或“零 locator”。
- 在没有稳定数据、固定相机状态或应用测试桥接的情况下，承诺任意 Canvas 应用均可生成稳定回归测试。
- 承诺零改动黑盒模式与增强接入模式具有相同的稳定性、成本和 CI 可信度。

### 4.3 分级接入模型

所有用户从无需修改源码的 L0 或 L1 开始，并可按实际瓶颈逐步增强：

| 等级 | 被测项目改动 | 主要能力 |
| --- | --- | --- |
| L0 黑盒 | 无 | DOM／Canvas 探索、视觉操作、问题报告、基础测试生成 |
| L1 配置增强 | 无源码改动 | 登录态、固定环境、允许域名、网络忽略／模拟规则 |
| L2 可测试 DOM | 少量可选改动 | `data-testid`、ARIA、稳定 locator 和更可靠回放 |
| L3 Canvas Bridge | 可选测试适配模块 | 实体、相机、图层、选中状态和场景加载的确定性验证 |

用户拒绝或暂时无法进行 L2／L3 改造时，系统仍应允许继续使用 L0／L1 能力，并明确展示覆盖范围、稳定性等级和限制。

## 5. 功能需求

### FR-01 项目与测试环境配置（P0）

用户可以创建测试项目并配置：

- 项目名称和 Base URL。
- 允许访问的域名列表。
- Playwright `storageState` 或由用户手动完成一次登录后保存的会话。
- 测试账号、环境变量和测试数据；敏感值必须加密存储且在日志中脱敏。
- 默认运行限制：最大步骤数、最长时间和最大模型调用次数。

验收标准：

- 未在允许列表中的 URL 不得访问。
- 过期登录状态应被识别并给出明确错误，不得被误判为产品缺陷。
- 日志和截图元数据中不得出现明文密码、Token 或 Cookie。

### FR-02 应用接入与兼容性扫描（P0）

用户无需提供源代码仓库即可通过以下流程开始接入：

1. 输入测试环境 URL 和允许访问的域名。
2. 在交互式浏览器中完成一次登录，系统保存可复用的 Playwright `storageState`；也允许直接上传已有状态。
3. 系统以只读、低风险方式扫描页面和主要导航入口。
4. 系统生成应用兼容性报告、初始项目配置和建议测试场景。

扫描至少识别：

- DOM 元素、ARIA 信息、稳定属性和候选 locator。
- Canvas／WebGL、iframe、Shadow DOM、复杂编辑器和文件上传控件。
- Console 异常、关键网络请求、第三方域名和常见异步加载模式。
- 登录状态、跳转链路、会话失效和可能阻塞自动化的验证码／MFA。
- 可以直接稳定测试、需要视觉 fallback、需要自适应回放和暂时无法可靠自动化的区域。

兼容性报告至少包含：

- 当前接入等级和无需修改源码即可使用的能力。
- 页面类型、可操作元素和 Canvas／WebGL 区域概览。
- 建议的域名允许列表、网络忽略规则、viewport 和运行限制。
- 低稳定区域及其原因。
- 可选的最小改造建议，例如增加 `data-testid`、测试数据重置接口或 Canvas App Bridge；建议不得阻止用户继续使用黑盒模式。

验收标准：

- 对一个可访问的历史 Web 应用，用户可以在不修改源码的情况下，于 15 分钟内完成登录、扫描和第一次探索运行。
- 扫描过程不得执行提交订单、删除、发布、发送或其他高风险写操作。
- 扫描完成后自动创建一份可编辑的项目配置和至少一个示例场景。

### FR-03 自然语言测试场景（P0）

用户可以创建场景，至少包含：

- 场景名称。
- 前置条件。
- 测试目标。
- 可选测试数据。
- 预期结果。
- 禁止执行的操作。

系统应在描述明显缺少必要信息时提示用户补充；不应自行猜测账号、金额等关键业务数据。

示例：

```text
前置条件：已使用普通用户登录，购物车为空。
目标：搜索“无线鼠标”，打开第一个有库存的结果并加入购物车。
预期：购物车数量增加为 1，商品名称与详情页一致。
禁止：提交订单或进入真实支付页面。
```

### FR-04 AI 探索执行（P0）

系统根据当前页面和场景目标循环执行“观察—计划—动作—验证”：

- Playwright 采集 URL、页面标题、DOM／Accessibility、可见文本、截图、Console 和 Network，形成精简的页面 Observation。
- Agent Planner 根据测试目标、当前 Observation 和历史步骤决定下一动作；Playwright 本身不负责理解业务语义。
- 在 L0／L1 模式下，优先使用无需修改源码的运行时能力：DOM／Accessibility 读取、页面公开状态、Console／Network 监听、Canvas 边界与相对坐标、视觉锚点，以及用户显式配置的网络忽略／模拟规则。
- DOM 元素优先通过 ARIA role、label、可见文本、`data-testid` 和稳定属性识别，并使用 Playwright locator 执行。
- 当结构化信息不足，或目标位于 Canvas／WebGL 内部时，Computer Use／视觉适配器根据截图提出视觉目标或坐标动作。
- Computer Use／视觉适配器只负责视觉理解和动作建议，不直接拥有浏览器；点击、输入、滚动和拖拽最终统一由 Playwright Executor 执行。
- 对 Cesium 等可注入测试能力的应用，优先使用应用测试桥接读取实体 ID、相机状态、选中状态和目标屏幕坐标，再由 Playwright 执行交互。
- 每次只执行一个或一组可回滚的低风险动作，然后重新观察页面。
- 动作前检查元素是否可见、可用、稳定且未被遮挡。
- 对重复页面、无进展状态和动作循环进行检测并主动停止。
- 达到目标、确认失败或触发资源限制时结束运行。

每个探索步骤必须标记执行模式：

- `locator`：AI 选择语义目标，Playwright 使用 DOM／Accessibility locator 执行。
- `visual`：Computer Use／视觉适配器根据截图提出动作，Playwright 使用 mouse／keyboard／touch 等接口执行。
- `app_bridge`：通过应用测试桥接解析 Canvas 语义目标或状态，再由 Playwright 执行或验证。

验收标准：

- 每个动作都要记录目标、定位依据、执行模式、Computer Use 是否触发、动作参数和动作结果。
- 连续三次无有效进展时停止，并生成“无法继续”的诊断。
- 禁止把屏幕坐标作为生成回归测试的唯一 locator。
- 对 Canvas 的视觉点击必须确认坐标处于目标 Canvas 边界内，并在执行后验证页面或应用语义状态确实发生预期变化。

### FR-05 运行证据采集（P0）

每次运行必须采集：

- 每一步动作前后的截图。
- URL、页面标题和关键 DOM／Accessibility 摘要。
- 每个步骤的 `executionMode`、locator／视觉目标、Computer Use 触发原因和坐标来源。
- 应用提供测试桥接时，采集关键 Canvas 状态，例如相机、可见实体、选中实体和瓦片／资源加载状态。
- Playwright trace。
- 浏览器控制台的 error 和未捕获异常。
- 失败的资源请求和 HTTP 4xx／5xx；允许配置忽略规则。
- 场景开始、结束时间和每一步耗时。
- 使用的模型、推理次数和估算成本。

用户可以按时间顺序查看完整轨迹，并定位到问题发生前后的步骤。

### FR-06 问题发现与结构化报告（P0）

MVP 支持以下问题类型：

1. 场景目标未完成。
2. 明确预期结果不满足。
3. 页面出现未处理异常、控制台错误或关键请求失败。
4. 元素遮挡、文本明显截断、关键按钮不可见或无法操作。
5. 成功／失败状态与实际操作语义不一致。
6. 页面进入空白、死循环或长时间无响应状态。
7. Canvas／WebGL 中的关键对象不可见、不可交互、未正确高亮或交互后语义状态未变化。

每个问题至少包含：

- 标题和问题类别。
- 建议严重级别：Blocker／High／Medium／Low。
- AI 置信度。
- 实际结果与预期结果。
- 最小复现步骤。
- 发生问题时的截图和相关日志。
- 判断依据；必须区分事实证据与 AI 推断。

AI 不确定时应标记为“需要人工确认”，不能将猜测描述成确定缺陷。

### FR-07 人工审核（P0）

用户可以对运行结果执行：

- 确认或驳回问题。
- 修改问题标题、严重程度和预期结果。
- 选择哪些探索步骤保留为回归用例。
- 对不稳定或包含敏感操作的步骤进行编辑或删除。

所有人工修改需保留修改记录，供后续评估问题准确率。

### FR-08 Playwright 测试生成（P0）

系统把用户确认的路径生成 TypeScript 测试：

- 优先使用 `getByRole`、`getByLabel`、`getByText`、`getByTestId` 等可维护 locator。
- 使用 Playwright 原生自动等待和 web-first assertions。
- 对测试数据、Base URL 和凭据使用配置或环境变量，不硬编码秘密。
- 生成的代码应包含清晰的测试名、步骤分组和必要注释。
- 对不稳定 locator 给出警告，并建议应用增加 `data-testid` 或可访问性属性。
- 对 Canvas 探索步骤，优先生成“语义实体 ID → 运行时屏幕位置 → Playwright 鼠标动作”的代码，不得直接固化探索时的绝对坐标。
- 如果视觉步骤无法转换为稳定 locator、应用测试桥接调用或可解释的视觉检查，应标记为需要人工处理，不能计入稳定回归用例。
- AI 语义判断不能直接成为不可解释的布尔断言；必须转化为确定性条件，或保留为单独的人工审核检查。

每个生成步骤必须标记稳定性等级，测试整体等级取其中最低等级：

| 等级 | 含义 | 默认用途 |
| --- | --- | --- |
| A 确定性 | 稳定 DOM locator、明确断言或应用测试接口 | 可作为稳定回放和 CI 候选 |
| B 相对稳定 | Canvas 相对位置、稳定视觉锚点或受控环境下的几何定位 | 可稳定回放，但必须展示风险提示 |
| C 自适应 | 运行时需要 Computer Use 重新寻找语义视觉目标 | 仅用于自适应回放，不作为严格 CI 门禁 |
| D 暂不可自动化 | 验证码、硬件认证或无法可靠验证的操作 | 生成说明和人工步骤，不生成可执行假象 |

对于 C 级步骤，保存的应是目标语义、视觉依据和安全约束，不得保存一次探索产生的裸绝对坐标作为长期定位方式。

用户可以预览、编辑、复制和下载生成的测试文件。

### FR-09 稳定与自适应回放（P0）

用户可以从产品内选择两种回放方式：

**稳定回放**

- 由 Playwright 执行固定测试代码，默认不调用 AI 或 Computer Use 决定每一步动作。
- Canvas 回放优先使用固定测试环境、相对几何定位、应用测试桥接和 Playwright mouse／keyboard 动作。
- 主要承载 A／B 级步骤，是未来 CI 门禁的候选模式。

**自适应回放**

- Playwright 仍是唯一浏览器执行层；仅在 C 级视觉步骤或 locator 无法恢复时，由 Computer Use 根据当前截图重新寻找语义目标并提出动作。
- 必须由用户显式选择或由测试配置启用，不得在稳定回放失败后静默切换。
- 每次视觉 fallback 必须记录触发原因、截图、模型、动作建议、实际动作和验证结果。
- 自适应结果具有概率性，成本和耗时更高，默认不得作为严格 CI 门禁。
- Computer Use 无法确认目标时必须失败或请求人工确认，不得猜测后继续。

两种模式均应在成功时显示耗时和断言结果，在失败时保存 trace、截图、控制台和网络信息。用户可以手动发起一次“AI 分析失败原因”，但分析不得改变测试结果。

失败原因至少分为：产品缺陷、locator 失效、测试数据／账号问题、环境问题、时序问题和无法判断。

### FR-10 运行结果页面（P0）

结果页至少展示：

- 运行状态：通过、发现问题、未完成、系统错误、人工确认中。
- 场景目标和完成情况。
- 时间线式步骤轨迹。
- 每个步骤展示 `locator`、`visual` 或 `app_bridge` 执行模式，以及视觉 fallback 的触发原因。
- 展示当前接入等级、回放模式、步骤／测试稳定性等级和可用于 CI 的建议。
- 问题列表及证据。
- 生成测试代码。
- 运行耗时、模型调用次数和估算成本。

MVP 可只支持单用户和最近运行列表，不要求复杂团队权限与统计看板。

### FR-11 安全控制（P0）

- 浏览器运行在隔离容器中，默认无内网访问能力。
- 只允许访问项目配置的域名。
- 页面内容视为不可信输入，不能覆盖系统测试目标或安全规则。
- 密码输入、Token、Cookie 和用户配置的敏感字段在截图／日志／模型上下文中按策略处理。
- 对删除、提交订单、支付、发送邀请、发布内容等动作设置阻断或人工确认。
- 运行结束后销毁或清理临时浏览器环境。

## 6. P1：MVP 后的优先候选

以下内容不应阻塞 MVP 发布：

- GitHub Pull Request 和 CI 集成。
- 根据代码 diff 推荐受影响场景。
- Firefox、WebKit 和移动视口。
- 失败测试的 locator 修复建议和代码 PR。
- 多环境变量集、数据驱动测试和批量运行。
- 团队、角色、项目权限和审计日志。
- 历史趋势、重复问题聚类和缺陷去重。
- Jira／GitHub Issues 等缺陷系统集成。
- 基于页面状态图的覆盖率展示。

## 7. 建议技术架构

### 7.1 核心组件

1. **Web Console／API**：项目配置、场景输入、运行控制和结果展示。
2. **Onboarding／Compatibility Scanner**：录制登录、扫描页面能力、判断接入等级并生成初始配置和改造建议。
3. **Run Orchestrator**：运行状态机、资源限制、重试和中止。
4. **Agent Planner**：理解目标、选择下一动作、判断进展和提出问题。
5. **Playwright Executor**：探索和回放阶段共用的唯一浏览器执行层，提供 locator、mouse、keyboard、截图和 trace 等接口。
6. **Observation Collector**：通过 Playwright 采集截图、DOM／Accessibility、console、network 和 trace，并生成精简 Observation。
7. **Visual／Computer Use Adapter**：根据截图理解 Canvas／视觉目标并提出动作；不得绕过 Playwright Executor 直接操作浏览器。
8. **Canvas App Bridge Adapter**：以可选、可替换的应用测试接口读取 Canvas 语义状态；首个参考实现面向 Cesium。
9. **Issue Judge**：结合明确断言与 AI 语义分析生成问题候选。
10. **Test Compiler**：将确认后的轨迹转换为 Playwright TypeScript，并将视觉探索步骤稳定化和分级。
11. **Artifact Store**：保存截图、trace、报告和生成代码。

### 7.2 执行原则

- **黑盒优先**：先以 L0／L1 完成接入和测试；L2／L3 是提升稳定性的可选增强，不得成为首次运行的硬前置条件。
- **结构化信息优先**：DOM／Accessibility → 应用测试桥接 → 视觉定位 fallback。
- **统一执行**：无论动作来自 locator、应用测试桥接还是 Computer Use，最终浏览器动作均由 Playwright 执行。
- **确定性优先**：能用传统断言验证的结果，不交给 LLM 判断。
- **AI 只处理高价值不确定性**：场景理解、探索决策、语义问题和失败诊断。
- **探索与回放分离**：探索可以动态决策并调用 Computer Use；稳定回放无模型依赖，自适应回放仅在显式启用时调用 Computer Use，二者均不得把一次运行产生的裸坐标作为长期定位方式。
- **模型可替换**：Agent 层不直接绑定单一模型厂商的专用动作格式。
- **Canvas 语义可观测**：对于 Cesium 等重 Canvas 应用，通过测试环境专用桥接接口提升可验证性，而不是完全依赖像素判断。

### 7.3 Canvas App Bridge 最小契约

当用户选择 L3 增强接入时，建议由被测应用在测试构建中暴露统一入口；名称可调整，参考适配器至少提供以下能力。未提供该接口的应用仍可继续使用 L0／L1 黑盒能力：

```ts
window.__WEB_AI_TEST__ = {
  version: "1",
  getSceneState(),
  listVisibleTargets(),
  getTargetScreenPosition(targetId),
  getSelectedTargetId(),
  waitForSceneReady()
};
```

- `getSceneState()`：返回相机、时钟、图层和加载状态的精简快照。
- `listVisibleTargets()`：返回当前可交互目标的稳定 ID、类型和必要业务标签。
- `getTargetScreenPosition(targetId)`：把语义目标转换为当前 viewport 内的坐标；Playwright 使用该坐标执行 mouse 动作。
- `getSelectedTargetId()`：用于确定性验证 Canvas 点击结果。
- `waitForSceneReady()`：等待必要的瓦片、实体和渲染状态就绪，禁止用固定 sleep 替代。

Cesium 参考适配器可以在内部使用 `scene.pick`、实体集合、相机状态和世界坐标到屏幕坐标的转换能力，但不应把 Cesium 专用对象泄露到通用 Agent／Test Compiler 接口中。

## 9. 非功能需求

### 9.1 可靠性

- Orchestrator 和浏览器进程异常退出后，运行应进入明确的失败状态。
- 相同场景可使用相同测试数据重新运行。
- 每个运行和步骤使用唯一 ID，日志可关联查询。

### 9.2 性能与成本

- 默认单场景上限：10 分钟、50 个浏览器动作；具体数值可配置。
- 在结果页展示模型调用次数、Token 或供应商成本估算。
- 页面无变化时不得持续发送完整截图和 DOM，应使用摘要或差异降低成本。

### 9.3 隐私

- 敏感配置加密存储。
- 日志与模型输入进行字段级脱敏。
- 支持配置运行工件的保留时间和手动删除。

### 9.4 可评估性

- 保存人工对问题的确认／驳回结果。
- 支持固定基准场景和缺陷注入版本。
- 模型、Prompt 或执行策略升级前后可以在同一基准集上对比。
- 统计 locator、visual 和 app_bridge 三种执行模式的占比、成功率、耗时和成本。
- 统计视觉 fallback 触发率，以及视觉步骤成功转换为稳定 Playwright 代码的比例。
- 分别统计 L0～L3 各接入等级的场景完成率、稳定回放率和人工介入率。
- 统计 A～D 各稳定性等级的步骤／测试数量，以及 C 级自适应回放的触发率、成功率、耗时和成本。
- 零改动基准必须记录被测应用源码修改数量，并保持为 0；Runner 配置、测试账号和浏览器登录录制不计为源码修改。

### 9.5 Canvas／WebGL 稳定性

- 固定 viewport、device scale factor、浏览器版本和必要的 GPU／WebGL 运行参数。
- 固定 Cesium 初始相机位置、时钟、测试数据、图层和动画状态。
- 提供明确的 `waitForSceneReady`／`waitForTilesLoaded` 等条件，禁止仅用固定 sleep 判断渲染完成。
- 记录浏览器、GPU、WebGL renderer、地图数据和关键资源版本，便于失败复现。
- 应用测试桥接只在测试环境开启，不得向生产环境暴露敏感内部状态或高权限操作。
- 对无法控制硬件和渲染差异的场景使用容差或语义断言，不承诺跨环境像素完全一致。

## 10. 开发阶段建议

### 阶段 A：执行与证据底座

- 完成 Playwright locator／mouse／keyboard 动作 API、隔离浏览器、运行状态机和证据采集。
- 完成交互式登录录制、`storageState` 管理和 Onboarding／Compatibility Scanner 的最小闭环。
- 使用至少一个无源码改动的历史 Web 应用验证 URL → 登录 → 扫描 → 首次运行流程。
- 暂时使用人工指定动作验证执行链路。

### 阶段 B：Agent 探索

- 接入观察—计划—动作循环。
- 接入 Visual／Computer Use Adapter，完成 locator、visual、app_bridge 三种执行模式的选择和记录。
- 完成域名限制、循环检测、步骤／时间限制和高风险动作拦截。

### 阶段 C：问题报告与测试编译

- 输出结构化问题候选。
- 完成人工审核、A～D 稳定性分级和 Playwright TypeScript 生成。
- 完成稳定回放与显式启用的自适应回放；验证不得静默从稳定模式切换为自适应模式。
- 定义通用 Canvas App Bridge 协议，并实现可选的最小 Cesium 参考桥接：相机状态、实体列表、实体屏幕位置、选中状态和场景加载完成状态。

### 阶段 D：稳定性评估

- 建立至少 30 个场景的内部基准集；若首批目标包含 Cesium，至少 10 个场景应覆盖 Canvas 选择、缩放、拖拽、图层、相机和实体状态。
- 基准集至少包含一个完全不修改源码的历史 DOM 应用，以及一个完全不修改源码的 Cesium／Canvas 与 DOM 混合应用。
- 注入常见功能、网络、前端异常和视觉问题。
- 根据完成率、缺陷准确率、回放稳定性和成本决定是否进入试点。

## 11. 研发启动前需要确认的产品决策

1. MVP 是本地部署、私有部署还是 SaaS；建议早期采用单租户或本地 Runner。
2. 首批目标应用类型：普通 DOM 应用、Cesium／Canvas 与 DOM 混合应用，或两者同时支持；本版建议明确包含后者。
3. 登录态由用户上传 `storageState`，还是通过产品中的交互浏览器录制。
4. 哪些动作必须人工确认，以及是否允许项目管理员自定义规则。
5. 第一版是否需要导出完整 Playwright 项目，还是只导出单个 `.spec.ts`。
6. 运行工件默认保留时间，以及截图中个人数据的处理要求。
7. 是否支持客户自带模型 Key；建议执行层和模型层从第一天解耦。
8. 第一版 Visual／Computer Use Adapter 是否直接接入 OpenAI `computer` 工具，同时是否保留自定义视觉模型适配接口。
9. 可选应用测试桥接的统一命名、权限边界和最小接口集合；建议使用只在测试构建中启用的 `window.__WEB_AI_TEST__`，但不得将其设为 L0／L1 接入前置条件。

## 12. MVP 完成定义（Definition of Done）

当一个新用户能够在 15 分钟内完成以下流程，即可认为产品闭环成立：

1. 在不修改被测应用源码的情况下创建项目并连接一个历史测试环境。
2. 设置或录制登录状态，完成兼容性扫描并看到当前接入等级、可直接测试范围和可选增强建议。
3. 用自然语言创建一个 3～10 步业务场景。
4. 启动 AI 黑盒探索并查看实时／完成后的动作轨迹。
5. 在目标应用包含 Canvas 时，至少完成一次 DOM 操作和一次 Canvas 交互，并能说明各步骤使用的执行模式。
6. 查看至少一种带截图和日志的结构化问题，或确认场景通过。
7. 审核探索路径并生成可读、且不包含裸屏幕坐标的 Playwright TypeScript 测试或自适应测试描述。
8. 查看每个步骤和测试的 A～D 稳定性等级、依据及 CI 建议。
9. 在同一环境中完成一次稳定回放或显式启用的自适应回放，并能查看所有视觉 fallback 证据。
10. 下载测试文件和运行报告。
