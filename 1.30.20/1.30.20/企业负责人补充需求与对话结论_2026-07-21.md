> 整理日期：2026-07-21（Asia/Shanghai）  
> 来源：用户提供的企业负责人对话总结，不是逐字聊天原文。  
> 关系：作为 `web-ai-testing-mvp-requirements.md` 0.3 版的补充输入，不覆盖原文；出现冲突时必须记录并向用户确认。  
> 安全：本文不记录内网 URL、测试账号、密码、Cookie、Token 或 API Key。

版本语境说明：本次对话发生时，用户是依据原始 V2 ZIP（现正式映射为 `AI-GUI 1.20.00`）向负责人介绍能力；不能用后来增强的 `1.25.00` 反推当时回答。

## 1. 已确认的产品定位

1. 首个企业目标系统是带 Cesium 地图框架的 Web 仿真类应用，包含 agent、实例、动力学等垂直业务术语。
2. 产品仍必须保持通用 Web 测试框架定位，底层测试逻辑应可复用于电商等其他 Web 项目，不能把核心执行器硬编码为 Cesium 专用工具。
3. 第一版采用分级接入，默认不要求目标系统源码；用户填写部署 URL 后，应能使用绝大多数核心黑盒测试功能。
4. Cesium／Canvas 的目标站适配建立在通用 Web、DOM、视觉适配器和可选 App Bridge 分层架构上；目标站专用逻辑必须放在适配层。

## 3. 顶层目标模式的产品要求

### 3.1 默认交互

- 场景默认输入应围绕：业务目标、必要测试数据、预期业务结果、禁止动作。
- 不要求用户编写“先点什么、再点什么”的流程文本。
- 执行角色和前置条件只有在真实进入 Planner Prompt、策略或验收判断时才可保留；否则移到可选高级设置或删除。
- “生成规则测试计划”不能作为顶层目标模式的唯一主路径；固定计划可保留为调试／确定性回归工具，逐步 Agent 才是企业目标模式。
- 人工审核仍保留，但审核对象应是 AI 探索轨迹和拟生成回归路径，而不是强迫用户事前编写完整点击步骤。

### 3.2 动态执行边界

1. AI 接收不可变业务目标、项目／环境／场景配置和最新脱敏 Observation。
2. AI 每次只提出一个受 Schema 约束的动作、完成、阻塞或澄清请求。
3. Playwright 始终是动作执行器；视觉模型／Computer Use 只负责在语义定位不足时提供建议。
4. 每步执行后必须重新采集页面／场景状态并判断是否取得进展。
5. 删除、退款、支付、提交订单、发布、邀请等高风险动作必须受禁止动作和人工确认策略约束；示例目标不等于自动授权真实退款或支付。

## 4. 陌生垂直业务的辅助方案

建议新增“项目业务上下文包”，作为项目级可编辑配置，而不是把领域知识写死在系统提示词中。最小内容包括：

- 领域简介和业务目标边界。
- 术语表：例如 agent、实例、动力学对象及企业实际定义。
- 业务对象、关键属性、状态机和允许的状态转换。
- 页面／Canvas 中对象与业务语义的对应关系。
- 典型目标、反例、成功条件和禁止动作。
- 可选 App Bridge 能力说明和语义目标列表。
- 来源、更新时间和审核人，确保上下文可追溯。

运行时遵循以下原则：

1. 优先使用项目明确提供的上下文和页面事实，不用通用常识覆盖企业定义。
2. 同一术语存在多义或缺少关键参数时，进入“需要澄清”，不能静默猜测。
3. 探索成功后的人工审核结果可沉淀为示例场景或术语补充，但必须经人工确认后才进入项目上下文。
4. 业务上下文只增强理解，不绕过域名、权限、禁止动作、秘密引用和人工确认边界。

## 5. 环境与测试分工

- 企业内网系统当前不适合远程直接接入；本文不保存其地址或账号。
- 外网开发阶段可使用公共测试站完成通用框架逻辑，但必须遵守站点规则，只执行已获授权且低风险的测试。
- Cesium 官方站可用于验证地图／Canvas 基础交互相似性，但不能代替企业内网目标系统的最终验收。
- 真实内网测试由企业指定成员执行时，应使用统一版本、场景、环境配置和验收清单，并回传脱敏的运行编号、报告、截图／Trace 完整性及失败分类。
- 电商类外部网站用于验证通用性，不自动视为版本规则中的“第二个正式适配网站”；只有用户明确指定并完成适配验收后才进入 `1.30.20`。

## 7. 版本归属

- `1.25.x`：继续补齐企业需求的开发版本，可包含目标优先 UX、业务上下文包、FR-05／06／11 和通用 Cesium 能力建设。
- `1.30.00`：完成补充需求中的可复用通用能力和本地功能验收；必须具备通用 Cesium／Canvas 能力，但不包含 ER-07／ER-08 公共站验证或企业目标站验收。
- `1.30.10`：完成 ER-07 Cesium 官方站／安全公共站验证，以及第一个企业测试网站适配、内网授权环境联调、30 场景×5 次重复基准及企业级 Definition of Done。
- `1.30.20`：完成 ER-08 至少一个非 Cesium 业务站通用性验证及第二个正式网站适配。
- Cesium 官方站和公共电商站在开发期属于验证环境，不自动占用 `10／20` 的正式网站适配编号。
- 对话中的“V3”是当时的迭代称呼；从 2026-07-21 起正式版本规则以 `AI-GUI 1.25.00 → 1.30.00` 为准，不再把“V3”作为正式发布号。

## 8. 仓库与每日进度流程

- 企业指定仓库：`https://github.com/GaeainCloud/AI-GUI-Autotest`。
- 计划流程：本地完成代码与验证 → 检查敏感／大文件 → 提交并推送 → AI 根据真实提交与测试结果生成比赛平台摘要 → 人工确认后发布。
- 本次整理没有执行 GitHub 推送，也没有向比赛平台发布内容；外部提交必须由用户明确发起。
- 公共仓库禁止提交：真实账号／密码／Token／API Key、Cookie／storageState、DPAPI 文件、内网 URL、客户数据、`.venv`、运行截图／Trace／报告中可能含敏感内容、构建缓存和无关历史归档。
- 每日摘要至少包含：版本号、提交范围、关联需求、真实测试结果、已知问题、下一步和提交链接；不能用未执行的测试或计划中的功能充当完成结果。

## 9. 尚需用户／企业确认

1. 此次新确认的 Cesium 目标是否意味着立即恢复此前暂停的 FR-04，还是仍先完成 FR-05／FR-06。
2. 执行角色和前置条件是从默认页面移除，还是保留在高级设置并真实进入 Planner。
3. 项目业务上下文由谁维护，允许哪些格式，是否需要文档上传／检索；上传内容的权限和敏感信息边界尚未确认。
4. 企业目标系统首批必须覆盖的 Cesium 操作清单及成功语义，例如选择、缩放、拖拽、图层、相机、实体状态。
5. 哪些退款、删除、支付、提交和发布动作必须人工确认，测试环境是否提供可安全回滚的数据。
6. GitHub 公共仓库的分支策略、每日提交截止时间、比赛平台内容模板和是否允许提交构建产物。
