## 1. 文档目的和结论

这份文档按对话和仓库验收记录的时间顺序，说明项目是怎样从最初的“能调用浏览器和模型的 AI-GUI 工程样机”，逐步演进为具有真实浏览器执行、分步 Agent、视觉观察、结果验证、恢复契约、审批、安全隔离、证据和报告的工程版本。

必须先区分四种“通过”：

1. **代码已实现**：源码中有对应模块和逻辑。
2. **自动化回归通过**：单元、集成、浏览器离线或接口测试通过。
3. **运行包可启动**：前端、后端、Python、Chromium、Docker Runner 和 API 合约可用。
4. **真实网站业务闭环通过**：在真实登录、真实数据和真实网络环境中，关键业务结果被独立后置条件验证。

## 2. 阶段一：最初项目盘点和问题暴露

### 2.1 用户最初的目标

最初目标不是编写一条固定脚本，而是给系统任意网站后，让它能够：登录、扫描页面控件和功能、理解业务流程、逐步操作、发现错误、截图、分析报错原因和复现步骤，并完成测试闭环。

后续进一步明确：最终产品仍然要泛化，但当前先把两个网站跑通：

- `http://192.168.31.218:7991`：内网建模、3D 编辑器、想定和仿真相关流程；
- `https://ion.cesium.com`：复杂异步网页、资产和 3D/WebGL 相关流程。

### 2.2 对 1.32.00 初始状态的判断

早期项目已经不是空壳，具备 React/Vite 前端、FastAPI 后端、Playwright 执行器、AI Planner、Runner、审批、安全策略、截图、DOM、Accessibility、Console、Network、Trace、报告和恢复骨架。早期阶段的工程判断约为：普通界面主流程 80%、安全和证据 75%、AI 通用决策 45%～55%、跨网站兼容性 45%～55%、两个真实目标网站验收 20%～35%、整体交付稳定性 55%～65%。这些是当时的工程评估，不是最终验收数字。

### 2.3 当时发现的根本问题

- `agent_planner.py` 过大，包含大量 Cesium 专项判断、等待判断、登录判断和动作修正；AI 不是唯一业务决策者，而是“规则 + 模型 + 站点修正”的组合。
- 复杂控件、Shadow DOM、跨域 iframe、Canvas/WebGL、动态 SPA 和无名称控件虽然能够被识别，但很多只会被标记为 adaptive 或 blocked，不能继续完成业务。
- 早期 Node Playwright 与 Python Playwright 版本存在不一致风险。
- 恢复机制更擅长安全停止，不擅长确认业务结果后的安全恢复；点击成功不等于业务成功。
- 真实内网账号、测试数据、三维语义观察和网站可达性不足，不能用本地测试替代真实验收。
- 源码、运行版、ZIP 和静态前端包有时间差，导致“启动哪个副本”经常被混淆。

### 2.4 关键决策

项目没有继续盲目堆叠“万能规则”，而是先收敛为两个可验收垂直能力包，再保留将来泛化的 Agent 内核：

- 站点能力包提供术语、业务关系、合法选项、特殊组件知识和结果验证条件；
- Agent 负责观察当前页面、理解目标、决定下一步业务动作；
- 确定性执行器只负责可靠执行已经批准的动作；
- 安全策略可以否决危险动作，但不能替代 Agent 的业务决策。

## 3. 阶段二：把“固定脚本”改成分步观察和 Agent 决策

### 3.1 形成的行业参考方向

对话中参考和讨论了 mabl、Playwright、Stagehand、OpenAdapt、Browser Use、UI-TARS、Hercules、AgentLab、BrowserGym、WebArena 和 OSWorld。形成的原则是：

- Playwright 负责可靠的语义定位、等待、Trace 和浏览器证据；
- Stagehand 类方案负责 AI 与确定性动作的混合；
- mabl 类方案采用“首次探索较慢、成功流程稳定回放、页面变化时智能修复”；
- OpenAdapt 类方案强调结果验证、受控修复和不确定时暂停；
- UI-TARS 类视觉能力作为 Canvas/WebGL、无名称图标和空间关系的升级层；
- BrowserGym/AgentLab 主要用于评测，不冒充生产运行内核。

最终形成的六层方向是：页面观察、变化分类、决策路由、多模态 Agent、动作契约执行、验证与恢复。

### 3.2 用户明确的 Agent 原则

用户多次强调：每进入新页面、弹窗、向导步骤、下拉或级联组件，都要重新扫描当前 DOM、无障碍树、截图和页面状态，再判断下一步；旧技能包只能加速或提供参考，不能强制覆盖当前 Agent 判断；页面变化、连续点击无进展或定位失败时，必须重新观察、换策略、回退或暂停，而不能死磕旧链路。

因此代码逐步加入了：

- 单步决策，不一次生成整条不可验证链路；
- 每步动作前后观察和截图；
- 当前页面事实高于历史经验和能力包；
- 同一页面状态下失败的动作/定位指纹不得原样重试；
- 持久写入结果不明确时，不允许更换定位器盲目重放；
- 连续无进展达到阈值后安全停止或澄清；
- CompletionGate 独立判断目标是否真正达成。

### 3.3 写入权限的变化

初期为了安全，真实创建、保存、上传和提交被拦截。用户明确说明：如果一律不允许真实写入，就无法测试目标网站本身的创建 Bug，因此最终采用了窄范围授权：

- 普通输入、下拉和级联选择可作为向导内临时状态继续执行；
- 最终“创建”、保存、提交和更新仍属于副作用动作，需要目标授权、审批、资源名、回滚和结果验证；
- 只允许本次明确分配的测试对象进入专用策略，不允许覆盖、删除或修改未知业务对象；
- API Key 继续只在请求内存中保存，不写入报告和磁盘。

这解决了“安全策略把测试完全拦死”和“为了跑通而无条件放开写入”之间的冲突。

## 6. 阶段五：恢复闭环、检查点、探索图和评测体系

### 6.1 2026-08-12～13 的架构完善

本阶段将“失败后不能死机”从口头要求变成运行内契约：

- 每个动作前后保存页面身份、页面状态、验证结果和是否允许重放；
